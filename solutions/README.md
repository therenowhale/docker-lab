# Ответы к Docker-лаборатории

Открывай этот файл только после своего прогноза и проверки. Ошибиться в прогнозе — нормально: именно так и появляется понимание.

## Лаба 01 — namespaces и cgroups

Контейнер — процесс на хосте, запущенный с изоляцией и учётом ресурсов; это не виртуальная машина. PID namespace показывает процессу собственное дерево процессов: поэтому Java — PID 1 **внутри** контейнера, но имеет другой PID на хосте. Mount, UTS (hostname), network и PID namespaces изолируют разные представления системы. Cgroups учитывают и ограничивают ресурсы. Их связь с процессом видна в `/proc/self/cgroup`, а лимиты и фактическое потребление — в `docker inspect` и `docker stats`. Ядро остаётся общим с хостом.

## Лаба 02 — слои и кеш

Каждая инструкция Dockerfile создаёт результат, который зависит от своих входных данных. Правка `src` инвалидирует `COPY src` и последующие шаги, но сохраняет кеш зависимостей. Правка `pom.xml` инвалидирует `COPY pom.xml` и `mvn dependency:go-offline`. Поэтому `pom.xml` копируется раньше исходников: изменение Java-кода не должно заново скачивать зависимости. `docker history` показывает историю слоёв, но не является полным аудитом безопасности.

## Лаба 03 — multi-stage

Этап `build` содержит Maven, кеш зависимостей, исходники и собранный JAR. В финальный этап копируется только JAR и используется JRE. Это уменьшает состав production-образа и убирает build-инструмент, но не делает образ автоматически безопасным: остаются обновления базового образа, зависимости, права и конфигурация.

## Лаба 04 — PID 1 и сигналы

JSON-форма `ENTRYPOINT` запускает Java напрямую. Docker посылает SIGTERM Java-процессу PID 1, поэтому shutdown hook выполняется. SIGKILL перехватить нельзя, поэтому hook не успеет сработать. При shell-форме или shell-обёртке без `exec` PID 1 может стать shell, который не передаст сигнал Java или плохо обработает дочерние процессы.

## Лаба 05 — сеть и DNS

Compose создаёт bridge-сеть и внутреннюю DNS-запись для сервиса `app`. Клиент обращается к нему как `app:8080`. `localhost` внутри client-контейнера означает сам client, а не хост и не Java-сервис. Публикация `8088:8080` нужна для доступа с Mac, но не для общения контейнеров друг с другом.

## Лаба 06 — хранилища

Named volume управляется Docker и сохраняется после удаления контейнера. `down -v` удаляет том, поэтому marker пропадает. Bind mount отображает конкретную папку Mac внутри контейнера, сохраняя права и привязку к этому компьютеру. Named volume подходит для данных сервиса, bind mount — для разработки и явной интеграции с файлами хоста.

## Лаба 07 — ограничения

`docker compose config` показывает объявленные лимиты; их применение подтверждают `docker inspect` и `docker stats`. При жёстком лимите Java может получить `OutOfMemoryError`, либо ядро завершит процесс (часто exit code 137). JVM учитывает cgroup-лимиты, но heap — только часть памяти: есть native-память, metaspace и стеки потоков. Поэтому heap нельзя бездумно выставлять равным лимиту контейнера.

## Лаба 08 — healthcheck и диагностика

Docker исполняет заданную команду healthcheck; здесь она проверяет `/health`, а не `/ready`. Поэтому `/not-ready` меняет готовность приложения, но не Docker health. Healthcheck сам не перезапускает контейнер. Диагностику начинай с `docker compose ps`, затем изучай логи, `docker inspect` (state, exit code, историю healthcheck) и сеть/порты. Не удаляй всё подряд — потеряешь доказательства и, возможно, чужие данные.

## Лаба 09 — non-root

`USER app:app` даёт скомпрометированному процессу меньше прав внутри контейнера. Это не защищает от уязвимостей ядра, опасных volumes/смонтированного Docker socket, утёкших секретов, уязвимых зависимостей и злоупотребления сетью. `read_only: true` — сильное следующее улучшение, но потребует явно дать writable-mounts, например для `/tmp` или данных. Удаление capabilities тоже может сломать законную функцию приложения.
